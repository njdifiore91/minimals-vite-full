# JWT Keys Management for Kong API Gateway

## Overview

This directory contains the public keys used by the Kong API Gateway to validate JSON Web Tokens (JWTs) issued by the authentication service. The system implements RS256 asymmetric key signing for enhanced security, with the private keys securely stored in the authentication service and only public keys available to the API Gateway for validation.

## Directory Contents

This directory should contain the following files:

- `public_key_current.pem`: The current public key used for JWT validation
- `public_key_previous.pem`: The previous public key (maintained for rotation periods)
- `public_key_next.pem`: The next public key (pre-positioned for upcoming rotation)
- `keys_metadata.json`: Metadata file containing key IDs and validity periods

## JWT Validation Process

The Kong API Gateway uses the JWT plugin to validate tokens with the following configuration:

- **Algorithm**: RS256 (asymmetric key signing)
- **Token expiry**: 60 minutes
- **Refresh token validity**: 7 days
- **Validation checks**:
  - Token expiration (exp claim)
  - Token issuer (iss claim)
  - Token audience (aud claim)
  - Signature verification using public keys

When a request arrives at the API Gateway, the JWT plugin:

1. Extracts the JWT from the Authorization header
2. Verifies the token's signature using the appropriate public key
3. Validates the token's claims (expiration, issuer, audience)
4. If valid, allows the request to proceed to the backend service
5. If invalid, returns a 401 Unauthorized response

## Key Rotation Process

To maintain security, JWT signing keys are rotated regularly following this process:

1. A new key pair is generated by the authentication service
2. The new public key is deployed to this directory as `public_key_next.pem`
3. The authentication service begins issuing tokens with both current and new keys
4. After a transition period, the keys are rotated:
   - `public_key_previous.pem` is archived or deleted
   - `public_key_current.pem` becomes `public_key_previous.pem`
   - `public_key_next.pem` becomes `public_key_current.pem`
5. The `keys_metadata.json` file is updated with new key IDs and validity periods

This rotation process ensures that valid tokens continue to work during the transition period while maintaining strong security practices.

## Security Best Practices

### Key Management

- **Private keys** must never be stored in this directory or any public repository
- Public keys should be generated with a minimum of 2048 bits (4096 bits recommended)
- Key rotation should occur at least every 90 days
- Previous keys should be maintained only as long as tokens signed with them might still be valid

### Token Security

- Tokens must be stored in `sessionStorage` (not `localStorage`) on the client side
- Tokens must be transmitted only over HTTPS connections
- Token payloads should contain minimal information to reduce exposure
- Sensitive data should never be included in token payloads

### API Gateway Configuration

- Rate limiting should be enabled to prevent brute force attacks
- IP filtering should be configured for administrative endpoints
- CORS policies should be properly configured to prevent unauthorized cross-origin requests
- Request transformation should sanitize headers and parameters

- **Authentication Service**: Issues and manages JWTs
- **Data Service**: Validates user permissions after authentication
